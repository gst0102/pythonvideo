## 1. 项目背景与目标

本项目原先围绕“悦享互动宝”阶段二能力推进，已经沉淀了 FastAPI 后端基础能力，包括用户登录、积分账户、积分流水、签到、小游戏、激励广告、会员支付、邀请关系、二级分销、提现、后台基础接口和 QA 验收流程。

项目目前方向调整为“网盘资料互助 + 积分解锁资源”的微信小程序 MVP。用户可通过签到、小游戏、广告、上传资源、补链、完成求资源任务等方式获得积分，也可以消耗积分获取网盘资源链接、提取码、解压码等信息。

新的产品定位应尽量使用低风险表达，例如：

- 网盘资料互助平台
- 学习资料库
- 办公模板库
- 自媒体素材库
- 团长资料库
- 公开资料索引
- 求资源悬赏平台

不建议在产品名、首页文案、审核材料中突出“盗版影视”“最新影视资源”“盗版课程”“会员资源共享”等高风险表达。

## 2. 当前阶段目标

当前阶段不是继续开发旧影视订阅模块，而是基于现有后端项目做资源业务域重构规划。

当前明确目标：

1. 保留现有后端商业底座，不重新另起完整后端项目。
2. 隔离旧 `/anime` 影视资源模块，不把它硬改成万能资源库。
3. 新增通用 `resources` 资源域，用于网盘资料资源、资源解锁、上传审核、求资源、投诉失效、补链和后台管理。
4. 小游戏保留，作为“赚积分页”的固定入口。
5. 支付、会员、邀请关系、二级分销、提现保留，但前端文案建议收敛为“邀请奖励/收益记录”，避免直接强调“分销/返佣”。
6. 下一步优先做微信小程序静态原型，使用 mock 数据，不接后端。

## 6. 已知问题和风险

### 6.1 产品和合规风险

- 网盘资源项目的核心风险不是技术，而是内容合规和资源质量。
- 影视娱乐分类可以存在，但上线种子资源和文案建议优先使用学习资料、办公模板、自媒体素材、团长资料、公开资料索引等低风险内容。
- 未解锁资源前不得泄露完整网盘链接、提取码、解压码、备用链接。

### 6.2 技术风险

- 旧 `anime_resources` 模型偏影视语义，不适合直接扩展为通用资源表。
- 新资源域需要新增数据表、接口和状态机，不能只改前端 mock 后直接上线。
- 当前仓库没有完整小程序前端工程，下一步如果做静态原型，需要先创建前端目录结构。

### 6.3 积分和资金 P0 风险

- 获取资源重复扣积分。
- 获取资源重复奖励上传者。
- 扣积分成功但未展示链接。
- 展示链接成功但未扣积分。
- 求资源悬赏冻结、采纳、退回不一致。
- 补链奖励重复发放。
- 小游戏或广告重复发积分。
- 支付回调重复导致重复发积分或重复邀请奖励。
- 二级邀请奖励比例错误。
- 退款后奖励未失效或未处理。
- 提现冻结、成功、失败退回不一致。

### 6.4 当前阶段二遗留风险

此前阶段二验收报告中曾发现目标数据库迁移、D+2 兜底真实执行、真实广告失败链路、历史配置隔离、退款后奖励处理等仍需目标环境确认。

这些不应阻塞“静态原型”开发，但在后端重构和上线前必须重新进入 QA 验收。

## 10. 关于“下个窗口是否直接开发静态原型”的建议

建议：可以。

更准确地说，下个窗口适合直接做：

```text
微信小程序静态原型 + mock 数据 + 蓝绿色 UI
```

暂时不要做：

- 后端资源接口
- 积分真实扣减
- 支付接入
- 二级分销改动
- 数据库迁移

原因：

1. 新产品方向刚切换，先用静态原型确认信息架构和页面体验，风险最低。
2. 当前仓库没有完整小程序工程，先搭静态壳可以快速明确前端目录、页面路由、组件风格。
3. 资源获取、积分扣减、支付、邀请奖励都是 P0 后端风险，应该等页面闭环确认后再按测试清单开发。
4. mock 原型可以直接给用户看体验，避免后端先做错方向。
