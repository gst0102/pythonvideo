# 悦享互动宝阶段二 v2：eCPM 结算规则重构开发文档

## 1. 背景与目标

当前阶段二 MVP 的积分规则主要基于固定积分发放设计，适合快速搭建任务体系，但不适合长期承接小游戏广告收益和 eCPM 波动。

现阶段业务已经明确以下现实约束：

1. 广告 eCPM 不是固定值，无法长期向用户承诺固定收益积分。
2. 运营侧通常在次日下午才能拿到上一日较完整的广告数据，包括 eCPM、广告曝光 PV、有效点击、总收益等。
3. 前台仍然需要给用户即时反馈，否则用户会感知“玩了没结果”。
4. 平台不希望频繁改规则，避免用户感知为“收益随意调整”，从而导致信任下降和流失。

因此，阶段二需要从“固定即时积分模型”升级为：

- 签到采用固定积分到账；
- 小游戏采用预估积分展示；
- 次日下午对昨日数据做正式结算；
- 如运营未及时录入，则在第三天按最近 7 天平均 eCPM 自动兜底确权；
- 后续若拿到真实数据，再通过差额补正流水修正，不直接推翻用户已见规则。

本补充文档用于统一后续开发、测试、验收和运营口径。

---

## 2. 核心规则升级说明

### 2.1 规则升级目标

本轮规则升级要同时满足以下目标：

1. 用户觉得“有机会赚到积分”，并且过程反馈清晰。
2. 平台不会因为 eCPM 波动而频繁改口径。
3. 后台可以基于真实经营数据结算，保证整体不亏损。
4. 积分账务、提现口径、前台展示、后台统计要一致。

### 2.2 核心规则结论

本轮明确采用以下经营模型：

1. 签到积分：固定到账。
2. 游戏积分：先展示预估积分。
3. 游戏积分正式结算时间：次日下午。
4. 若昨日运营数据未录入：第三天自动按最近 7 天平均 eCPM 兜底确权。
5. 后续若有真实数据：只做差额补正，不直接改写用户已见历史结果。

### 2.3 为什么不继续使用固定积分

如果继续使用固定积分，会产生以下问题：

1. 平台收益与用户积分支出脱钩，长期容易失衡。
2. 运营很难根据实际广告收益做及时调控。
3. 当真实收益和用户固定积分长期偏离时，后续再改规则会更伤用户信任。

因此，本轮采用“固定签到 + 预估游戏 + 次日结算”的组合，是兼顾用户体验与经营稳定性的最小可行方案。

## 3. 用户前台展示口径

### 3.1 前台统一表达原则

前台仍然统一展示“积分”，不把复杂收益公式直接暴露给普通用户。

用户端只理解三类核心概念：

1. 今日预估积分
2. 昨日已结算积分
3. 总积分

现金口径尽量收缩，仅保留：

1. 已提现金额

除已提现金额外，其余收益、返佣、奖励尽量全部积分化表达。

### 3.2 首页展示建议

首页核心卡片建议展示：

1. 今日预估积分
2. 昨日已结算积分
3. 总积分
4. 今日任务进度

首页文案建议强调：

- 今日互动任务产生的是预估积分；
- 昨日积分将在次日下午更新为正式结算结果；
- 若结算数据延迟，会按平台规则自动先行结算。

### 3.3 我的页展示建议

我的页建议展示：

1. 总积分
2. 今日预估积分
3. 昨日已结算积分
4. 已提现金额
5. 可提现积分
6. 锁定中积分

不建议在我的页同时大量展示各种金额字段，否则用户会误以为平台收益口径频繁变化。

### 3.4 积分明细页展示建议

积分明细页需明确区分来源和状态，至少支持以下类型：

1. 签到固定积分
2. 游戏预估积分
3. 游戏正式结算积分
4. 游戏差额补正积分
5. 邀请返佣积分
6. 会员赠送积分
7. 提现锁定积分
8. 提现成功积分
9. 提现退回积分

## 4. 会员四档权益矩阵

本轮先采用四档等级，不增加“无限档”。

四档为：

1. 普通用户
2. 月卡会员
3. 季卡会员
4. 年卡会员

### 4.1 默认权益矩阵

以下数值作为本轮默认初始值写入开发文档，同时要求 PC 后台可调整：

| 等级 | 每日小游戏次数 | 邀请返佣系数 | eCPM 积分系数 |
|---|---:|---:|---:|
| 普通用户 | 20 | 0% | 20% |
| 月卡会员 | 100 | 40% | 40% |
| 季卡会员 | 200 | 50% | 60% |
| 年卡会员 | 300 | 60% | 80% |

### 4.2 权益解释原则

1. 每日小游戏次数是用户最直接感知的任务权益。
2. 邀请返佣也统一以积分形式呈现，不再优先展示现金佣金。
3. eCPM 积分系数是游戏积分正式结算的重要参数。
4. 本轮默认值写死用于开发和测试，但后台必须支持修改。

### 4.3 配置生效原则

后台调整后的权益参数，建议只对调整生效日之后的新任务和新结算生效。

不建议直接影响历史已结算积分，避免造成历史账务混乱。

## 5. 签到规则设计

### 5.1 签到口径

签到采用固定积分到账，不采用 eCPM 次日结算模型。

原因：

1. 签到是基础留存动作，规则越稳定越好。
2. 签到积分通常金额较小，没必要做复杂波动结算。
3. 用户对签到最在意的是“顺手拿到一点奖励”，而不是追求精确收益换算。

### 5.2 签到面板设计方向

当前首页点击签到无跳转到签到面板，需要补成完整交互。

签到面板建议具备以下设计元素：

1. 独立签到面板，而不是只在首页状态卡点击。
2. 视觉上采用金币、宝箱、日历或盲盒式卡片设计。
3. 日历上展示连续签到状态。
4. 周日用红色或高亮背景标记。
5. 支持“随机彩蛋感”，但真实账务仍以固定基础规则为准。

### 5.3 推荐签到规则

本轮采用：

1. 固定基础积分
2. 随机彩蛋视觉
3. 连续签到奖励
4. 周日特殊展示或额外奖励

“随机彩蛋视觉”指用户面板上可看到 `1-5` 这类惊喜反馈，但系统真实账务不应完全依赖纯随机发放，以避免规则波动过大。

### 5.4 签到规则说明原则

签到面板要明确写出：

1. 每日可签到 1 次
2. 连续签到可触发额外奖励
3. 特殊日可有加成
4. 同日不可重复领取

## 6. 小游戏预估积分与广告领取规则

### 6.1 小游戏积分口径

小游戏不再简单承诺固定最终积分，而是：

1. 当局完成后给出预估积分反馈
2. 次日下午根据昨日真实数据做正式结算

### 6.2 用户看到的即时反馈

小游戏仍然必须给用户即时正反馈，否则体验会变差。

推荐即时反馈口径：

1. 完成一局后提示本局“预估积分”
2. 页面明确说明“小游戏积分受每日广告权益和次日结算影响”

### 6.3 广告领取规则

本轮默认采用以下规则：

1. 玩完一局后，引导进入激励广告流程
2. 完整观看广告后，提示：“恭喜你获得 X 预估积分”
3. 未完整观看广告后，提示：“很抱歉，本局未获得积分”

这意味着本版规则下，小游戏收益与广告完整观看绑定。

### 6.4 为什么这样设计

原因如下：

1. 能保持用户即时获得结果反馈；
2. 能更稳定地把用户收益与广告收益挂钩；
3. 能防止用户误以为“不看广告也能稳定刷收益”；
4. 更符合“平台不亏、用户有机会拿积分”的经营目标。

### 6.5 小游戏页面展示建议

小游戏页面建议新增或强化以下元素：

1. 今日预估积分展示
2. 今日剩余次数展示
3. 当前用户等级展示
4. 本局预估积分展示
5. 广告领取状态展示
6. “积分为预估，次日下午结算”说明

## 7. 次日结算、7 日均值兜底与差额补正流程

### 7.1 日常结算节奏

推荐结算流程如下：

1. 用户在 `D 日` 完成小游戏，系统记录预估积分
2. 运营在 `D+1 下午` 获取昨日广告数据
3. 运营通过后台录入或确认昨日 eCPM、PV、有效点击、总收益等关键值
4. 系统按昨日规则生成正式结算积分

### 7.2 第三天兜底规则

若 `D+1` 未完成录入，则在 `D+2` 对 `D 日` 结算执行兜底规则：

1. 使用最近 7 天平均 eCPM 作为参考值
2. 自动生成该日正式结算积分
3. 标记该日为“7 日均值兜底结算”

这样可以避免用户长时间看不到昨日结算结果。

### 7.3 后补真实数据规则

若兜底结算后，后续又拿到真实数据，则：

1. 不直接删除原结算记录
2. 不直接回滚用户已见结果
3. 系统生成一条或多条差额补正流水
4. 差额可能为补发，也可能为扣减

这样既能保证账务真实，又能保持结算流程透明。

### 7.4 差额补正原则

差额补正需要满足：

1. 可审计
2. 可追溯
3. 可说明
4. 幂等

补正后的积分流水应能清楚说明：

1. 对应哪一天
2. 原因是“真实数据补录”
3. 是补发还是扣减

### 7.5 推荐结算公式方向

本轮开发文档先定义公式方向，不强制把所有细节写死：

游戏正式结算积分建议至少参考以下因子：

1. 用户当日有效互动量
2. 昨日真实或兜底 eCPM
3. 用户等级的 eCPM 积分系数
4. 平台配置的换算规则

文档层面先锁规则，不在本轮要求把具体精算公式公开给用户。

## 8. PC 后台结算与配置要求

### 8.1 本轮后台定位

本轮后台不再只是“预留数据”，而是要提供一个最小可用的运营结算后台。

后台至少要能支撑：

1. 广告位和广告场景查看
2. PV、广告完成数、有效点击、预估收益查看
3. eCPM 手动录入
4. 昨日积分正式结算
5. 7 日均值兜底状态查看
6. 后补差额调整
7. 会员权益参数调整

### 8.2 后台必须支持的模块

建议至少包含以下模块：

1. 游戏广告位管理
2. 每日广告数据录入
3. 每日积分结算管理
4. 用户积分差额补正记录
5. 等级权益配置
6. 后台操作审计

### 8.3 后台必须展示的数据

针对小游戏广告结算，后台至少展示：

1. 日期
2. 广告场景
3. 广告位 ID
4. 曝光 PV
5. 完整观看数
6. 有效点击数
7. eCPM
8. 预估收益
9. 实际收益
10. 预估积分总量
11. 正式结算积分总量
12. 差额补正积分总量

### 8.4 后台必须支持的配置

后台需要支持以下配置修改：

1. 四档用户每日小游戏次数
2. 四档邀请返佣系数
3. 四档 eCPM 积分系数
4. 特定日 eCPM 值
5. 结算说明备注

### 8.5 运营操作规则

建议运营流程固定为：

1. 每天下午录入上一日广告经营数据
2. 核对后提交结算
3. 若当天没录入，系统次日自动用近 7 日均值兜底
4. 若后续数据修正，再走差额补正

后台页面应明确展示该机制，减少运营和客服口径混乱。

## 9. 文案与用户信任策略

### 9.1 总体原则

本项目是积分增长和互动任务项目，不应给用户造成“固定赚钱承诺”的认知。

但也不能让用户感知为“平台随时改规则”。

因此话术原则为：

1. 不承诺稳赚
2. 不夸大收益
3. 强化即时反馈
4. 强化规则透明
5. 强化“预估”和“昨日结算”是平台固定机制

### 9.2 首页文案方向

推荐方向：

- 完成今日互动任务，可获得预估积分
- 昨日积分将在次日下午更新
- 若数据延迟，系统将按平台规则先行结算

### 9.3 游戏页文案方向

推荐方向：

- 完整观看广告后可领取本局预估积分
- 小游戏积分受每日广告权益和次日结算影响
- 今日完成越多，累计预估积分越高

### 9.4 我的页文案方向

推荐方向：

- 今日预估积分
- 昨日已结算积分
- 总积分
- 已提现金额

不建议前台大篇幅展示复杂金额换算说明。

### 9.5 邀请与会员文案方向

会员和邀请页面建议强调：

1. 会员可获得更高每日任务次数
2. 会员可获得更高返佣积分比例
3. 更高等级对应更高结算系数

但应避免使用以下高风险表达：

1. 稳赚
2. 保底回本
3. 看广告直接赚钱
4. 一定能提现多少

## 10. 数据与接口改造边界

### 10.1 本轮需要新增或改造的能力

后续开发需重点覆盖以下边界：

1. 首页摘要接口新增今日预估积分、昨日已结算积分字段
2. 我的页资产接口新增或重组预估与已结算口径
3. 积分流水接口新增预估、结算、补正类型
4. 游戏任务状态接口新增等级权益和规则说明字段
5. 后台新增 eCPM 录入、结算、补差相关接口或页面

### 10.2 本轮不直接推翻的已有能力

本轮为兼容升级，不应直接删除以下既有体系：

1. 现有 points_ledger 积分流水体系
2. 现有 withdrawal 提现链路
3. 现有会员购买与回调链路
4. 现有广告事件记录与广告轮换能力

现有能力应尽量通过扩展字段、扩展类型、补充接口实现升级。

## 11. P0 风险与验收重点

本轮规则升级后，以下问题必须视为 P0 风险：

1. 预估积分和正式结算积分无法对账
2. 同一局游戏重复生成预估积分
3. 未完整观看广告却获得游戏积分
4. 7 日均值兜底重复执行或执行错误
5. 真实数据补录后重复补差
6. 首页、我的页、积分流水、后台结算四方数据不一致
7. 用户等级系数应用错误
8. 后台修改权益后污染历史已结算数据
9. 用户可通过刷新、重复请求或重放事件刷预估积分或结算积分
10. 提现积分、总积分、已结算积分之间口径混乱

### 11.1 验收重点

测试和验收时必须重点确认：

1. 是否清楚区分“今日预估积分”和“昨日已结算积分”
2. 是否定义清楚 `D+1` 手动结算与 `D+2` 自动兜底规则
3. 是否明确了后补真实数据后的差额补正机制
4. 是否保证前端展示、积分流水、后台统计一致
5. 是否能作为下一轮测试清单和 Bug 单的输入基础
