# 生产迁移检查清单：网盘资源审核与通知

## 1. 迁移目标

- 确认生产库具备 Alembic 版本记录。
- 安全上线 `source_upload_id`、`netdisk_user_notifications` 等网盘资源审核/通知字段。
- 避免本地历史库“已有表但没有 `alembic_version`”的问题带到线上。

## 2. 上线前必须确认

| 检查项 | 操作 | 通过标准 |
|---|---|---|
| 数据库备份 | 先做完整备份 | 可回滚到迁移前状态 |
| 版本表 | 查询 `alembic_version` | 生产库存在且只有一个当前版本 |
| 当前版本 | 执行 `alembic current` | 输出符合预期，不报 `users already exists` |
| 待迁移内容 | 执行 `alembic history` / `alembic heads` | 只有一个 head，迁移链连续 |
| 目标字段 | 检查 `netdisk_resources.source_upload_id` | 字段存在或由迁移新增 |
| 目标表 | 检查 `netdisk_user_notifications` | 表和索引可正常创建 |
| 审核接口 | 上传审核通过 | 可选择普通 5、精选 10、官方 20 |
| 用户通知 | 审核通过/拒绝/确认失效 | 用户侧能看到通知记录 |

## 3. 如果生产库没有 `alembic_version`

不要直接执行 `alembic upgrade head`。

正确处理顺序：

1. 先备份生产数据库。
2. 人工检查核心表是否已经存在：`users`、`user_accounts`、`points_ledger`、`netdisk_resources`。
3. 对照迁移文件逐项确认字段和索引。
4. 如果表结构已经等价于某个历史版本，先执行 Alembic `stamp` 到对应版本。
5. 再从该版本执行后续 `upgrade`。
6. 如果结构不等价，先写一次“补齐差异”的专用迁移，不要在生产库手工乱改。

## 4. 本轮重点迁移验证

- `netdisk_resources.source_upload_id`：
  - 用于从资源追溯原上传记录。
  - 上传审核通过后必须写入。
  - 确认失效后才能找到上传者并生成待追缴。

- `netdisk_user_notifications`：
  - 用于小程序“我的消息”。
  - 记录审核结果、确认失效、待追缴通知。
  - 用户通知不等于积分流水，不参与积分余额计算。

## 5. 回滚关注点

- 如果迁移失败，先回滚数据库备份。
- 如果接口上线后异常，优先关闭前端审核操作入口，保留查询能力。
- 不要删除已有积分流水和待追缴记录。
- 通知表可以补发通知，但不能反向修改积分余额。

## 6. 上线后抽查

| 场景 | 预期 |
|---|---|
| 上传审核通过普通资源 | 资源表写入 `level=normal`、`cost_points=5` |
| 上传审核通过精选资源 | 资源表写入 `level=featured`、`cost_points=10` |
| 上传审核通过官方资源 | 资源表写入 `level=official`、`cost_points=20` |
| 上传审核拒绝 | 用户收到审核未通过通知 |
| 资源确认失效 | 用户收到确认失效/待追缴通知 |
| 小程序打开我的消息 | 能看到最近 100 条网盘通知 |

## 7. 未覆盖风险

- 本清单不替代生产 DBA 审核。
- 如果线上已经有手工改过的表结构，必须先做 schema diff。
- 多实例并发审核仍依赖积分流水幂等键和数据库唯一约束保护。
