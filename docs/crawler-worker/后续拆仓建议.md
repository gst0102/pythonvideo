# crawler-worker 后续拆仓建议

更新时间：2026-06-14

## 1. 当前阶段建议

当前不建议马上拆成独立 Git 仓库。

理由：

- 仍在 MVP 快速迭代。
- worker 还复用主项目模型和入库服务。
- 资源分类、去重、待审核池还会继续调整。
- 先保证稳定跑通，比拆仓更重要。

## 2. 什么时候适合拆仓

满足以下条件后，可以拆成独立仓库：

| 条件 | 说明 |
|---|---|
| 稳定运行 1 周以上 | 没有频繁崩溃、浏览器残留、重复入库 |
| 来源超过 4 个 | 例如 KDocs、LinuxDo、公众号、合作资源、网盘目录 |
| 多项目复用 | 不只服务悦享资源库 |
| 入库接口稳定 | worker 通过 API 入库，不再直接依赖主项目模型 |
| 需要单独扩容 | worker 数量和主后端部署节奏不同 |

## 3. 拆仓后的推荐结构

```text
yuexiang-crawler-worker/
├─ README.md
├─ docker/
│  └─ Dockerfile
├─ crawlers/
│  ├─ kdocs/
│  ├─ linuxdo/
│  └─ common/
├─ classifiers/
│  ├─ rule_classifier.py
│  └─ deepseek_classifier.py
├─ exporters/
│  ├─ json_exporter.py
│  └─ csv_exporter.py
├─ clients/
│  └─ yuexiang_api_client.py
├─ docs/
└─ tests/
```

## 4. 拆仓后的交互方式

拆仓后，worker 不应该直接连主项目数据库。

推荐：

```text
crawler-worker
  -> 采集 / 清洗 / 分类
  -> 调用主后端导入接口
  -> 主后端负责去重、审核、积分、入库
```

这样 worker 可以服务多个项目，每个项目只需要提供自己的导入接口。

## 5. 第一阶段先保留在同仓的原因

当前同仓优势：

- 部署简单。
- 修改快。
- 不需要维护两套 CI/CD。
- 数据结构变化时不用跨仓同步。

建议：先稳定运行一周，再决定是否拆仓。
